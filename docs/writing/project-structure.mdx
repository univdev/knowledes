# 프로젝트 문서 구조

프로젝트 문서는 “미래의 사람이 이 프로젝트를 다시 이해할 수 있는가”를 기준으로 작성합니다.
AI가 문서를 읽고 과거 의사결정의 배경을 복원할 수 있어야 하므로, 결과만 적지 말고 맥락과 대안을 함께 남깁니다.

## 최상위 구조

`docs`의 최상위 레벨은 프로젝트 단위로 구성합니다.
사이드바에서 가장 먼저 보이는 이름은 프로젝트 이름이어야 합니다.

권장 구조는 다음과 같습니다.

```text
docs/
  <project-slug>/
    _category_.json
    index.mdx
    architecture.mdx
    features.mdx
    operations.mdx
    decisions/
      0001-<decision-slug>.mdx
```

`<project-slug>`는 URL과 파일 경로에 쓰는 짧은 영문 이름입니다.
실제 화면에 보이는 프로젝트 이름은 `_category_.json`의 `label`에 적습니다.

```json
{
  "label": "<프로젝트 이름>",
  "position": 10,
  "link": {
    "type": "doc",
    "id": "<project-slug>/index"
  }
}
```

## `index.mdx`: 프로젝트 개요

프로젝트 최상단 문서입니다.
이 문서만 읽어도 프로젝트가 무엇이고 왜 존재하는지 이해할 수 있어야 합니다.

반드시 포함할 항목은 다음과 같습니다.

- 한 줄 설명: 프로젝트를 모르는 사람이 즉시 이해할 수 있는 요약
- 문제 정의: 어떤 문제를 해결하려는지
- 대상 사용자: 누가 쓰는지, 어떤 상황에서 쓰는지
- 핵심 가치: 이 프로젝트가 반드시 지켜야 하는 제품적/기술적 기준
- 현재 상태: 실험, 개발 중, 운영 중, 유지보수 중 등
- 주요 진입점: 앱, 웹, API, 저장소, 배포 URL, 관리자 도구
- 관련 문서: 아키텍처, 기능, 운영, 의사결정 문서로 이어지는 링크

좋은 개요는 마케팅 문구가 아니라 판단 기준을 제공합니다.
예를 들어 “빠르고 편한 서비스”라고 쓰는 대신, 어떤 사용자의 어떤 반복 작업을 줄이는지 적습니다.

## `architecture.mdx`: 아키텍처

아키텍처 문서는 시스템을 변경할 사람이 구조를 빠르게 파악하도록 돕는 문서입니다.

포함할 내용은 다음과 같습니다.

- 전체 구성: 프론트엔드, 백엔드, 데이터베이스, 외부 서비스
- 데이터 흐름: 사용자의 주요 행동이 시스템 내부에서 어떻게 처리되는지
- 모듈 경계: 각 모듈이 책임지는 것과 책임지지 않는 것
- 외부 의존성: 결제, 인증, 알림, 스토리지, 분석 도구 등
- 성능/보안/확장성 제약: 설계에 영향을 주는 비기능 요구사항
- 바꾸면 위험한 부분: 과거 장애나 강한 결합이 있는 영역

가능하면 다이어그램을 추가하되, 다이어그램만 두지 말고 설명을 함께 적습니다.

## `features.mdx`: 주요 기능

기능 문서는 “무엇을 제공하는가”보다 “왜 그렇게 동작하는가”에 초점을 둡니다.

기능별로 다음 항목을 작성합니다.

- 기능 목적
- 사용자 흐름
- 정상 시나리오
- 예외/오류 시나리오
- 권한과 접근 제어
- 관련 데이터
- 관련 코드 위치
- 관련 의사결정 문서

기능이 복잡하면 `features/` 디렉터리를 만들고 기능별 파일로 분리합니다.

## `operations.mdx`: 운영과 유지보수

운영 문서는 장애 대응과 반복 작업을 재현 가능하게 만듭니다.

포함할 내용은 다음과 같습니다.

- 로컬 실행 방법
- 빌드와 테스트 명령
- 배포 절차
- 환경 변수와 secret의 위치
- 로그와 모니터링 확인 위치
- 장애 대응 절차
- 백업/복구 방법
- 정기적으로 점검할 항목

secret 값 자체는 절대 문서에 적지 않습니다.
대신 “어디에 저장되어 있고 누가 접근 권한을 갖는지”만 적습니다.

## `decisions/`: 의사결정 기록

중요한 결정은 별도 문서로 남깁니다.
이 문서는 과거 선택을 방어하기 위한 기록이 아니라, 미래 변경자가 맥락을 잃지 않게 하는 기록입니다.

파일 이름은 시간순으로 정렬되도록 작성합니다.

```text
decisions/
  0001-use-managed-auth.mdx
  0002-store-events-in-postgres.mdx
```

각 의사결정 문서에는 다음 항목을 포함합니다.

- 상태: 제안됨, 채택됨, 폐기됨, 대체됨
- 날짜
- 배경
- 결정
- 고려한 대안
- 선택 이유
- 트레이드오프
- 결과와 후속 작업
- 관련 이슈, PR, 코드, 외부 문서 링크

결정이 바뀌면 기존 문서를 조용히 덮어쓰지 않습니다.
기존 문서의 상태를 `대체됨`으로 바꾸고 새 의사결정 문서를 추가합니다.

## 작성 품질 기준

문서는 다음 질문에 답할 수 있어야 합니다.

- 처음 보는 사람이 프로젝트의 목적을 설명할 수 있는가
- 변경자가 건드리면 안 되는 경계를 알 수 있는가
- 기능 동작의 예외 조건이 드러나는가
- 왜 이 기술과 구조를 선택했는지 알 수 있는가
- AI가 관련 문서를 읽고 작업 계획을 세울 수 있는가

답이 어렵다면 문서가 아직 충분히 상세하지 않은 것입니다.

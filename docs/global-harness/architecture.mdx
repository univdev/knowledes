# 전역 하네스 아키텍처

전역 하네스는 큰 규칙을 `AGENTS.md`에 두고, 실제 작업은 전용 서브에이전트에 맡기는 구조예요.
이렇게 하면 오케스트레이터가 너무 커지지 않고, 각 책임을 독립적으로 고칠 수 있어요.

## 구성 요소

### 전역 오케스트레이터

`/Users/univdev/.codex/AGENTS.md`가 전역 오케스트레이션의 중심이에요.
여기에는 언제 어떤 에이전트를 호출할지, 어떤 작업은 직접 하지 말아야 할지 같은 발동 규칙이 있어요.

오케스트레이터는 다음 작업을 직접 자세히 수행하지 않아요.

- PR 제목과 본문 작성
- GitHub PR 생성, 수정, 병합
- Knowledes 문서 적재
- 기존 프로젝트 지식 탐색

대신 해당 작업을 전용 서브에이전트로 넘겨요.

### `pull-request-manager`

PR 작업을 담당해요.
브랜치 상태, 원격 저장소, 검증 결과를 확인하고 PR 제목과 본문을 작성해요.
기본 규칙은 PR 제목과 본문을 한국어로 작성하는 것이에요.

### `knowledes-documenter`

작업이 끝난 뒤 지식 데이터베이스에 변경 맥락을 적재해요.
기능 추가, 수정, 삭제, 아키텍처 변경, 의사결정이 생겼을 때 Knowledes 문서를 갱신해요.

이 에이전트는 문서를 작성하기 전에 Knowledes를 최신 `main`으로 맞추고, 새 문서 브랜치를 만들어 작업해요.

### `knowledes-context-researcher`

기존 작업을 이어서 진행하기 전에 Knowledes에서 관련 지식을 먼저 찾아요.
프로젝트 개요, 아키텍처, 주요 기능, 운영 규칙, 의사결정 기록을 읽고 구현 전에 필요한 맥락을 요약해요.

### 기타 전문 에이전트

전역 하네스에는 스캐폴딩, 프론트엔드 UX 검토 같은 다른 전문 에이전트도 있어요.
각 에이전트는 자기 역할만 담당하고, 필요한 경우 오케스트레이터가 연결해요.

## 데이터 흐름

기존 기능을 수정하는 작업은 보통 다음 순서로 흘러요.

1. 사용자가 기존 작업을 이어서 진행해 달라고 요청해요.
2. 오케스트레이터가 `knowledes-context-researcher`에게 맥락 탐색을 맡겨요.
3. 맥락 요약을 바탕으로 구현을 진행해요.
4. 작업이 끝나고 PR 타이밍이 오면 `knowledes-documenter`가 변경사항을 Knowledes에 적재해요.
5. PR을 열어야 하면 `pull-request-manager`가 한국어 PR을 작성하고 GitHub 작업을 처리해요.

## 경계

전역 하네스는 프로젝트 코드를 직접 소유하지 않아요.
프로젝트별 세부 규칙은 각 프로젝트의 `AGENTS.md`나 `.Codex/skills`가 우선이에요.

전역 하네스는 공통 운영 규칙을 제공하고, 프로젝트 지식과 PR 흐름을 빠뜨리지 않도록 도와요.

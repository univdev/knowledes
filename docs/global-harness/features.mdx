# 전역 하네스 주요 기능

전역 하네스의 기능은 개발 자체보다 작업 흐름을 안전하게 만드는 데 초점을 둬요.

## 기존 맥락 먼저 탐색하기

기존 기능을 이어서 수정하거나 확장할 때는 구현 전에 Knowledes를 먼저 확인해요.

발동 예시는 다음과 같아요.

- `이어 하자`
- `기존 기능 수정해줘`
- `전에 하던 작업 계속`
- `이 프로젝트에 기능 추가해줘`
- `기존 맥락 보고 진행해줘`

이때 `knowledes-context-researcher`가 관련 프로젝트 문서를 읽고, 과거 결정과 제약을 요약해요.
관련 문서가 없으면 없다고 말하고, 작업 완료 후 문서를 채우도록 이어가요.

## 작업 완료 후 지식 적재하기

기능을 추가, 수정, 삭제한 뒤 PR을 올릴 타이밍이 오면 Knowledes에 변경 맥락을 남겨요.
사용자가 직접 `작업 사항을 적재해줘`, `문서화해줘`, `결정사항 기록해줘`처럼 요청해도 같은 흐름을 실행해요.

적재 대상은 다음과 같아요.

- 새 기능의 목적과 사용자 흐름
- 수정된 기능의 변경 이유와 영향
- 삭제된 기능의 제거 이유와 대체 동작
- 아키텍처나 운영 방식 변경
- 중요한 의사결정의 배경, 대안, 트레이드오프

## 한국어 PR 작성하기

PR 제목과 본문은 기본적으로 한국어로 작성해요.
프로젝트가 한국어 사용자-facing 문맥을 갖고 있으면 Toss식으로 부드러운 `-요`체를 선호해요.

다른 언어를 써야 하는 프로젝트 규칙이 있거나 사용자가 명시적으로 요청한 경우만 예외로 둬요.

## PR 작업 분리하기

오케스트레이터는 PR 제목이나 본문을 직접 쓰지 않아요.
PR 생성, 수정, auto-merge, squash merge 같은 GitHub 작업은 `pull-request-manager`가 담당해요.

이렇게 하면 PR 문체와 GitHub 작업 규칙을 한곳에서 관리할 수 있어요.

## 큰 작업은 기본 위임하기

범위가 넓은 구현, 여러 파일을 건드리는 리팩터링, 플랫폼 제약이 걸린 작업은 오케스트레이터가 혼자 바로 고치지 않아요.
탐색, 계획, 구현, 검증을 가장 맞는 전문 에이전트나 팀에 나눠 맡겨요.

Charlang 프로젝트 하네스도 같은 규칙을 갖고 있어요.
멀티 파일 변경, Apps in Toss 플랫폼 민감 작업, UI와 상태가 함께 바뀌는 작업은 사용자가 명시적으로 서브에이전트를 요청하지 않아도 위임을 기본값으로 봐요.

## UI 닫힘 애니메이션을 열림의 역방향으로 맞추기

사용자가 여는 UI는 닫힐 때도 열릴 때와 대응되는 애니메이션을 가져야 해요.
예를 들어 fade-in으로 열린 다이얼로그는 즉시 사라지지 않고 fade-out으로 닫혀요.

이 규칙은 특히 모바일 WebView에서 중요해요.
하단 시트, 다이얼로그, 오버레이가 갑자기 사라지면 사용자는 탭이 먹혔는지, 화면이 튄 것인지 구분하기 어려워요.
Charlang의 PRO 구매 다이얼로그도 이 기준에 따라 닫힘 애니메이션을 보완했어요.

## Knowledes 최신화 후 작업하기

Knowledes를 읽거나 수정하기 전에는 기본적으로 `main`으로 이동하고 `origin/main`을 fast-forward pull 해요.
로컬 변경 때문에 최신화할 수 없으면 오래된 문서를 현재 지식처럼 사용하지 않고, 막힌 상태를 보고해요.

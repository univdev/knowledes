# 지식 작업을 서브에이전트로 분리하기

## 상태

채택됨

## 날짜

2026-05-26

## 배경

처음에는 전역 하네스 규칙에 Knowledes 적재 조건과 작성 기준을 직접 넣었어요.
하지만 이렇게 하면 오케스트레이터가 문서 작성 세부 규칙까지 떠안게 돼요.
규칙이 늘어날수록 전역 `AGENTS.md`가 커지고, 발동 조건과 실제 작업 방법이 섞일 위험이 있었어요.

또 사용자는 기존 작업을 이어서 할 때도 Knowledes에서 관련 지식을 먼저 찾고, 그 맥락을 이해한 상태로 개발을 시작하기를 원했어요.
이 흐름은 문서 적재와 반대 방향의 작업이므로 별도 책임으로 분리하는 편이 자연스러웠어요.

## 결정

전역 오케스트레이터는 발동 조건과 위임 계약만 갖도록 했어요.
실제 지식 작업은 두 개의 전용 서브에이전트로 나눴어요.

- `knowledes-context-researcher`: 기존 작업을 이어서 할 때 Knowledes에서 관련 지식을 먼저 찾아요.
- `knowledes-documenter`: 작업 완료 후 변경사항과 의사결정을 Knowledes에 적재해요.

두 에이전트 모두 `/Users/univdev/Documents/knowledes`를 지식 데이터베이스로 사용해요.
Knowledes를 읽거나 수정하기 전에는 최신 `main`으로 맞추는 규칙도 포함했어요.

## 고려한 대안

- 전역 `AGENTS.md`에 모든 지식 적재 규칙을 직접 유지하기
- 문서 적재만 자동화하고, 기존 맥락 탐색은 사람이 요청할 때만 하기
- 하나의 에이전트가 탐색과 적재를 모두 맡기

## 선택 이유

오케스트레이터는 “언제 무엇을 호출할지”만 알아야 유지보수가 쉬워요.
문서 탐색과 문서 적재는 목적, 입력, 출력이 다르기 때문에 별도 에이전트로 나누는 편이 명확해요.

기존 맥락 탐색을 개발 전에 강제하면 과거 의사결정을 무시하고 같은 문제를 다시 푸는 일을 줄일 수 있어요.
작업 완료 후 적재를 강제하면 다음 작업자가 다시 같은 맥락을 찾을 수 있어요.

## 트레이드오프

작업 시작 전과 PR 타이밍에 추가 단계가 생겨요.
하지만 프로젝트가 늘어날수록 이 단계가 의사결정 누락과 문서 부채를 줄여줘요.

서브에이전트 호출이 불가능한 환경에서는 오케스트레이터가 같은 절차를 직접 수행하는 fallback이 필요해요.

## 결과와 후속 작업

전역 하네스에 `knowledge_context_retrieval`과 `knowledge_documentation` 섹션이 생겼어요.
각 섹션은 전용 에이전트에 넘겨야 할 입력과 fallback 규칙을 설명해요.

앞으로 기존 기능을 수정하거나 이어서 작업할 때는 먼저 Knowledes를 탐색하고, 작업이 끝나면 변경된 지식을 다시 Knowledes에 적재해요.
